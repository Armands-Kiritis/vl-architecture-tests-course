Section 1 · 4 min

A unit test checks what code does. An architecture test checks where it lives and what it talks to.

You already know unit tests: give the payslip calculator a salary and a tax table, check the net pay that comes out. That tests behaviour.

An architecture test never looks at results. It reads the code itself and checks it against house rules your team agreed on, such as "the payroll calculation logic never talks to the database directly". Think of a building inspector: they don't taste the food in the kitchen, they check that the fire exits aren't blocked.

A unit test asks

  • Does PayslipCalculator return 2,412.50 net for this employee?
  • Does an unpaid leave month give 0 net pay?
  • Does a negative hours value throw an error?

An architecture test asks

  • Does anything in the Domain layer use the database code?
  • Do controllers call repositories directly, skipping the service layer?
  • Does every class ending in Repository live in Infrastructure?

A layer is a group of code with one job: the API that receives requests, the business rules, the database access. Teams draw them as boxes on a diagram. A dependency is one piece of code using another: if PayslipCalculator calls SqlConnectionFactory, the calculator depends on it.

The problem is that the diagram lives on a wiki page and the code changes every day. One stray line slips past review, then another. An architecture test turns the diagram into a test that fails the build.

Section 2 · 4 min

The tool reads your compiled code, maps who uses whom, and checks the map against your rule

The app never starts. No database, no test environment, no browser. Checking code without running it is called static analysis, and it is why an architecture test finishes in seconds.

LoadRead the compiled code: the .dll in C#, the class files in Java.
MapList every dependency: which class uses which.
SelectPick the classes the rule is about, e.g. everything in Payroll.Domain.
CheckApply the condition: "must not use Payroll.Infrastructure".
ReportPass, or fail and name each class that broke the rule.

Here is the map for a small payroll service. Green arrows are allowed. The red one is what the test catches.

Why this matters to a QA

Once the domain code needs a database, you can no longer unit test the payroll rules on their own. Every test of a tax calculation now needs a database set up. The architecture test protects your fast tests.

Section 3 · 6 min

Your first architecture test is an ordinary xUnit test with four parts

In C#, the NetArchTest library gives you the rule-writing part. Add it to your test project once:

dotnet add package NetArchTest.Rules

Then write the rule from Section 2 as a test. It sits next to your unit tests and runs with dotnet test.

using NetArchTest.Rules;
using Xunit;

public class ArchitectureTests
{
    [Fact]
    public void Domain_should_not_depend_on_infrastructure()
    {
        var result = Types.InAssembly(typeof(PayslipCalculator).Assembly)
            .That()
            .ResideInNamespace("Payroll.Domain")
            .ShouldNot()
            .HaveDependencyOn("Payroll.Infrastructure")
            .GetResult();

        Assert.True(result.IsSuccessful,
            "Domain classes using Infrastructure: " +
            string.Join(", ", result.FailingTypeNames ?? Array.Empty<string>()));
    }
}

Runs with dotnet test · fails with the names of the classes that broke the rule

import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;

@AnalyzeClasses(packages = "com.visma.payroll")
class ArchitectureTest {

    @ArchTest
    static final ArchRule domainShouldNotDependOnInfrastructure =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..infrastructure..");
}

Runs with JUnit 5 · ".." means "this package and anything below it"

// .dependency-cruiser.js
module.exports = {
  forbidden: [
    {
      name: "domain-not-to-infrastructure",
      severity: "error",
      from: { path: "^src/domain" },
      to: { path: "^src/infrastructure" },
    },
  ],
};

Run: npx depcruise src --config .dependency-cruiser.js · reads import statements instead of compiled code

Every architecture test in every language has the same four parts. Find them in the C# version:

LoadTypes.InAssembly(…)Every class in the compiled project. An assembly is the .dll a C# project builds into. Any class from it works as the pointer.
Select.That().ResideInNamespace(…)Narrows it to the classes this rule is about.
Condition.ShouldNot().HaveDependencyOn(…)What those classes must not do.
Result.GetResult()Runs the check. FailingTypeNames lists who broke it.

Run it in CI, the pipeline that builds and tests every pull request automatically. Then nobody has to remember to run it.

Section 4 · 5 min

Start with one rule your team already agrees on, then add these four kinds

Most useful architecture rules fall into four groups. Each one below has its plain-language version first.

Layers point one way

Api uses Application, Application uses Domain. Never the other way round.

.That().ResideInNamespace("Payroll.Domain")
.ShouldNot().HaveDependencyOn("Payroll.Api")

Names match their home

Anything called …Controller lives in the Api layer, so people can find it.

.That().HaveNameEndingWith("Controller")
.Should().ResideInNamespace("Payroll.Api")

Modules keep their internals private

The absence module may use the tax module's public API, not its internal tables.

.That().ResideInNamespace("Payroll.Absence")
.ShouldNot().HaveDependencyOn("Payroll.Tax.Internal")

No circles

If Absence uses Tax and Tax uses Absence, neither can change alone. Java and TypeScript tools check this directly:

slices().matching("com.visma.payroll.(*)..")
    .should().beFreeOfCycles();
When the rule finds 40 old problems on day one

Don't skip the test. Record the existing violations as known exceptions and fail only on new ones. ArchUnit calls this "freezing" a rule. In NetArchTest you filter the known classes out of the selection. Then fix the old ones over time.

Section 5 · 6 min · hands-on

Exercise: stop controllers from reaching the database

This is the payroll service from Section 2, as files:

Payroll/ ├── Api/ namespace Payroll.Api │ └── PayslipController.cs ├── Application/ namespace Payroll.Application │ └── PayslipService.cs ├── Domain/ namespace Payroll.Domain │ ├── Employee.cs │ └── PayslipCalculator.cs └── Infrastructure/ namespace Payroll.Infrastructure ├── PayslipRepository.cs └── SqlConnectionFactory.cs
Your task

Last sprint, a payslip page showed a raw SQL error to a user. The controller had called PayslipRepository directly and skipped PayslipService, which handles errors. Write a NetArchTest rule so this can't happen again. Try it before opening the hint.

Hint

Start from the Section 3 test. You only change two strings: the namespace you select, and the namespace those classes must not use.

Solution 
[Fact]
public void Controllers_should_not_use_infrastructure()
{
    var result = Types.InAssembly(typeof(PayslipController).Assembly)
        .That()
        .ResideInNamespace("Payroll.Api")
        .ShouldNot()
        .HaveDependencyOn("Payroll.Infrastructure")
        .GetResult();

    Assert.True(result.IsSuccessful,
        "Controllers using Infrastructure: " +
        string.Join(", ", result.FailingTypeNames ?? Array.Empty<string>()));
}

Now prove it works. Add using Payroll.Infrastructure; and a call to PayslipRepository inside PayslipController, then run dotnet test. The test should fail and name Payroll.Api.PayslipController. Remove the line and it goes green. A rule you have never seen fail might be checking nothing (remember Section 3, question 2).

Cheat sheet

Everything from this course on one screen

The pattern

Load → Select → Condition → Result

Load the compiled code, pick the classes, say what they must (not) do, run it and read the names that failed.

Three things to remember

  • Rules name namespaces as text. Rename a namespace and the rule passes silently. Break it once on purpose.
  • Start with one rule the team already agrees on.
  • Old violations? Record them as exceptions. Never skip the test.

Words used in this course

Layer
A group of code with one job, such as the API, the business rules or the database access.
Dependency
One piece of code using another. A uses B means A depends on B.
Namespace
The address of a class in C#, like Payroll.Domain. Rules use it to pick classes.

The compiled .dll file a C# project builds into.
